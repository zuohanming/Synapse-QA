# Synapse QA V1 产品基线与归档设计

## 1. 背景

Synapse QA 已形成界面自动化、接口自动化、测试配置、执行调度、测试报告和系统治理等产品能力。当前产品信息分散在 `docs/PRD.md`、专项设计文档、每日更新和代码实现中，且部分接口自动化能力已经进入开发工作区，但尚未完成统一端到端验收。

本设计用于建立 V1 日常权威基线和不可静默改写的 V1 归档快照。它只调整产品文档体系，不修改业务代码、接口或数据库。

## 2. 已确认决策

- 采用“权威基线 + V1 固化归档包”的双层结构。
- 当前 API 测试用例、API 全局变量和 API Runner 批次链路纳入 V1 范围，但统一标记为“待验收”。
- 已验收能力和待验收能力必须分开表达，不将进入代码等同于正式交付。
- 现有 `docs/PRD.md` 保留为兼容入口，避免已有引用失效。
- V1 归档完成后原则上不再修改正文；事实错误通过勘误记录修正。

## 3. 方案选择

采用“基线文档集 + 归档快照”方案。

未采用单一大文档方案，因为需求、架构和交付状态变化频率不同，集中维护容易产生状态冲突。未采用完整发布资料包方案，因为部署手册、测试报告和发布操作超出本次产品经理侧需求与架构归档范围。

## 4. 文档结构

```text
docs/
├── product/
│   ├── requirements-v1.md
│   ├── architecture-v1.md
│   └── feature-status-v1.md
└── archive/
    └── v1/
        ├── README.md
        ├── requirements.md
        ├── architecture.md
        └── feature-status.md
```

### 4.1 日常权威基线

- `requirements-v1.md`：V1 产品定位、用户、范围、功能需求、业务规则、非功能要求、非目标和验收标准。
- `architecture-v1.md`：信息架构、产品能力分层、核心流程、业务对象关系和系统边界。
- `feature-status-v1.md`：逐项记录功能状态、范围说明、验证依据和待验收条件。

### 4.2 V1 归档快照

- `README.md`：记录版本号、归档日期、范围、状态口径、来源、已知限制、勘误方式和后续版本入口。
- 其余三份文档是封版时权威基线的冻结副本。

## 5. 内容边界

### 5.1 需求基线

需求基线包括：

- 产品定位、目标用户和核心价值；
- 界面自动化、接口自动化、测试配置、执行中心、报告、通知和系统管理；
- 核心用户流程与业务规则；
- 非功能需求、安全约束和版本非目标；
- 可执行的 V1 验收标准。

需求基线不记录实现类名、具体路由和临时开发任务。详细技术实现继续由现有架构文档和代码说明承载。

### 5.2 产品架构

产品架构包括：

- 菜单和信息架构；
- 测试资产、编排、执行、报告、治理五层产品能力；
- UI 自动化和 API 自动化业务闭环；
- 项目、产品、环境、测试资产、用例、批次、任务和报告的对象关系；
- Web 管理平台、平台 API、PostgreSQL 和执行器的系统边界；
- 变量优先级、请求头优先级、状态汇总、软删除和版本快照等关键规则。

### 5.3 功能状态

| 状态 | 定义 |
| --- | --- |
| 已交付 | 已实现并具有明确验证证据 |
| 待验收 | 已进入代码和产品界面，但尚未完成完整端到端验收 |
| 部分交付 | 主流程可用，但明确缺少部分能力 |
| V1 非范围 | 明确不属于 V1 产品承诺 |

不得使用“基本完成”“大致可用”“后续完善”等无法验收的状态描述。

## 6. V1 状态边界

以下能力属于 V1，但在完成统一验收前必须标记为“待验收”：

- API 测试用例的创建、编辑、校验、发布和版本管理；
- API 全局变量的作用域、敏感值和运行时解析；
- API 参数化数据集展开；
- API Runner 正式批次执行；
- 接口步骤提取、断言、失败策略和结果归档；
- API 批次执行结果进入统一报告。

其他能力根据仓库现有验证证据分别归入“已交付”或“部分交付”。没有实现证据的功能归入“V1 非范围”，不得写成产品承诺。

## 7. 维护与归档规则

- `docs/product/` 是日常权威来源，可以随验收状态更新。
- `docs/archive/v1/` 是封版快照，归档后不静默改写正文。
- 归档事实错误通过归档 `README.md` 的勘误记录修正。
- 新增功能进入 V1.1 或 V2，不回填为 V1 原始承诺。
- V1 缺陷修复可以记录为 V1 修订，但不能扩大 V1 功能范围。
- `docs/PRD.md` 保留并指向新的权威需求基线，不删除原路径。
- 文档变更同步记录当日每日更新；建立 V1 产品基线和归档体系时更新 `CHANGELOG.md` 的 `Unreleased` 章节。

## 8. 实施范围

本次归档实施只包括：

1. 创建三份 V1 权威产品文档。
2. 创建 V1 归档目录及四份冻结文档。
3. 将现有 `docs/PRD.md` 调整为兼容入口。
4. 更新每日记录和 `CHANGELOG.md`。
5. 检查文档链接、状态一致性、占位符和 Markdown 格式。

不包括：

- 修改业务代码、接口、数据库或运行配置；
- 补做尚未完成的 API 自动化功能；
- 生成部署手册、发布操作手册或完整测试报告；
- 规划或实现 V1.1、V2 新功能。

## 9. 验收标准

1. 三份权威文档之间不存在范围或状态冲突。
2. 归档快照与封版时的权威文档内容一致。
3. 每项功能均使用四种规定状态之一。
4. 核心流程、业务对象关系和系统边界均有明确说明。
5. API 自动化待验收能力没有被描述为已交付。
6. 旧 `docs/PRD.md` 路径仍然有效，并能导航到新基线。
7. 每日更新和 `CHANGELOG.md` 已同步记录。
8. 占位符扫描、内部链接检查、内容一致性检查和 `git diff --check` 通过。

## 10. 后续流程

本设计经用户审阅确认后，使用 `superpowers:writing-plans` 编写逐文件实施计划。实施阶段严格按计划创建权威基线和归档快照，并在完成后执行文档验收。
