# 性能测试模板操作手册

> 适用范围：Synapse QA 性能测试模块（压测方案、测试报告、定时规则）
> 压测引擎：Grafana k6
> 面向对象：测试人员、开发人员、性能测试负责人和系统管理员

## 1. 文档目标

本文说明如何创建和使用性能测试模板（系统中称为“压测方案”），并解释每个配置项、执行状态、监控指标、报告、基线和定时规则的含义。

推荐首次使用时按以下顺序操作：

1. 确认执行器在线且已安装 k6。
2. 新建压测方案。
3. 配置环境、请求、负载和阈值。
4. 发送一次冒烟请求，确认目标可访问。
5. 保存方案并触发执行。
6. 在测试报告中查看实时监控和最终结果。
7. 将稳定通过的执行设为基线。
8. 根据需要配置定时规则。

## 2. 功能入口

左侧菜单选择 **性能测试**，可进入三个页面：

| 页面 | 用途 |
| --- | --- |
| 压测方案 | 创建、编辑、查看、删除和触发性能测试模板 |
| 测试报告 | 查看执行状态、实时监控、阈值、趋势、诊断和基线对比 |
| 定时规则 | 使用 Cron 表达式定时触发指定压测方案 |

## 3. 使用前准备

### 3.1 执行器要求

- 至少有一个在线执行器。
- 执行器机器已安装 Grafana k6。
- k6 可通过系统 `PATH` 被执行器发现。
- 执行器具有访问被测系统的网络权限。
- 同一执行器默认一次只运行一个性能测试任务。

### 3.2 权限说明

| 权限 | 能力 |
| --- | --- |
| `perf.plan.read` | 查看方案、报告、基线、趋势、导出和定时规则 |
| `perf.plan.manage` | 新建、编辑、删除方案，设置或取消基线 |
| `perf.plan.execute` | 触发和取消性能测试 |
| `perf.plan.manage` + `perf.plan.execute` | 新建、编辑、启停和删除定时规则 |

管理员默认拥有上述能力。

## 4. 核心术语

| 术语 | 说明 |
| --- | --- |
| VU | Virtual User，虚拟用户数，表示同时执行请求逻辑的并发用户 |
| RPS | Requests Per Second，每秒请求数 |
| P50 | 50% 请求的耗时不超过该值，接近中位数 |
| P90/P95/P99 | 90%/95%/99% 请求的耗时不超过该值，用于观察慢请求尾部 |
| Error Rate | 请求失败比例，使用 `0~1` 小数；`0.01` 表示 1% |
| Stage | 梯度、峰值或极限测试中的负载阶段 |
| Think Time | mixed 场景每次请求后等待的时间，用于模拟用户思考间隔 |
| Threshold | 性能阈值；不满足时执行结果为“性能未达标” |
| Baseline | 通过的历史执行，用作后续性能变化的比较基准 |

## 5. 新建性能测试模板

进入 **性能测试 → 压测方案**，点击 **新增方案**。

页面包含四个主要区域：

1. 基本信息
2. 请求配置
3. 负载配置
4. 阈值设置

### 5.1 基本信息

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| 方案名称 | 是 | 最多 120 个字符，建议体现系统、接口和场景 |
| 项目/产品 | 是 | 决定可选择的测试环境 |
| 测试环境 | 否 | 关联产品环境及 Base URL；可在执行前临时覆盖 |
| 场景类型 | 是 | 六种负载模型之一 |
| 负责人 | 否 | 方案维护或结果跟进人员 |
| 标签 | 否 | 用于分类检索 |
| 优先级 | 否 | P0、P1、P2、P3 |
| 描述 | 否 | 记录测试目的、数据准备或注意事项 |

切换场景类型会重置当前负载参数。系统会要求确认，避免误清空已填写配置。

## 6. 六大场景模板

所有场景最大并发均为 **500 VU**。建议从低负载开始，确认被测环境、监控和测试数据正常后再逐步加压。

### 6.1 基准测试（baseline）

**适用场景**

- 验证脚本和环境可用性。
- 获取低并发下的响应时间基线。
- 作为后续性能回归比较的起点。

**配置项**

| 参数 | 说明 | 示例 |
| --- | --- | --- |
| 并发数 VU | 固定虚拟用户数 | `3` |
| 持续时间 | 固定运行时长 | `2m` |

**推荐模板**

```text
VU：3
持续时间：2m
```

### 6.2 梯度压力测试（ramp）

**适用场景**

- 逐步提高压力，观察性能拐点。
- 确认错误率或延迟开始明显上升的并发区间。

**配置项**

每个阶段包含：

- 阶段时长
- 目标并发

每个阶段必须配置合法的时长和不超过 500 的目标并发。当前实现允许目标并发在不同阶段上升或下降，因此也可在最后增加降压阶段。

**推荐模板**

| 阶段 | 时长 | 目标 VU |
| --- | --- | --- |
| 1 | `1m` | 10 |
| 2 | `1m` | 50 |
| 3 | `2m` | 100 |

### 6.3 峰值负载测试（peak）

**适用场景**

- 模拟促销、批处理或业务高峰。
- 验证系统在预期峰值下是否满足 SLA。

**配置项**

| 参数 | 说明 | 示例 |
| --- | --- | --- |
| 峰值 VU | 最高并发 | `150` |
| 爬坡时长 | 从低负载升至峰值的时间 | `2m` |
| 保持时长 | 峰值持续时间 | `30m` |
| 降压时长 | 从峰值降至 0 的时间 | `2m` |

生产环境执行峰值测试前，必须确认容量、业务低峰时间和回滚措施。

### 6.4 极限压力测试（stress）

**适用场景**

- 持续加压，寻找系统最大承载能力。
- 观察超时、错误和吞吐下降的临界点。

**配置项**

| 参数 | 说明 | 示例 |
| --- | --- | --- |
| 起始 VU | 第一阶段并发 | `10` |
| 步长 VU | 每阶段增加的并发 | `10` |
| 每阶时长 | 每个并发水平保持时间 | `1m` |
| 最大 VU | 停止加压的上限 | `500` |

起始 VU、步长 VU 和最大 VU 必须为正整数且不得超过 500。建议最大 VU 大于起始 VU；否则执行器不会继续增加并发，只运行起始并发阶段。

### 6.5 稳定性/耐久测试（soak）

**适用场景**

- 长时间稳定运行，观察性能是否逐步下降。
- 发现连接池、缓存或资源泄漏引起的请求侧趋势异常。

**配置项**

| 参数 | 说明 | 示例 |
| --- | --- | --- |
| 并发数 VU | 固定并发 | `100` |
| 持续时间 | 通常为 10 分钟到数小时 | `30m` |

平台只提供请求侧指标。CPU、内存、GC、数据库连接等资源指标应同时在 Prometheus、Grafana 或其他监控系统中观察。

### 6.6 混合场景压测（mixed）

**适用场景**

- 多个接口按业务比例混合执行。
- 模拟更接近真实用户行为的流量组成。

**全局参数**

| 参数 | 说明 | 示例 |
| --- | --- | --- |
| 全局 VU | 所有混合接口共享的并发 | `50` |
| 持续时间 | 混合流量运行时间 | `10m` |
| 思考时间 | 每次请求后的等待时间 | `500ms` |

**接口参数**

- 接口名称：必须唯一。
- 权重：本次迭代选中该接口的概率。
- Method：GET、POST、PUT、DELETE、PATCH。
- URL：绝对 HTTP(S) URL 或可由环境 Base URL 解析的相对路径。
- Headers：该接口独立请求头。
- Body：该接口独立请求体。

最多可配置 50 个接口。所有接口的权重合计必须等于 1，允许误差不超过 `0.000001`。

**示例**

| 接口 | 权重 | Method | URL |
| --- | --- | --- | --- |
| 查询商品 | 0.6 | GET | `/products` |
| 查看详情 | 0.3 | GET | `/products/1001` |
| 创建订单 | 0.1 | POST | `/orders` |

> 权重表示“每次迭代随机选中该接口的概率”，不是每秒固定请求数。

## 7. 请求配置

### 7.1 Method

支持：

- GET
- POST
- PUT
- DELETE
- PATCH

### 7.2 URL 与环境 Base URL

未选择环境时，普通场景应填写完整 HTTP(S) URL。保存接口当前不强制检查该格式，但缺少可解析基址的相对 URL 可能在 k6 运行阶段失败。

选择环境后，可填写：

- 完整 URL
- 根相对路径，例如 `/api/orders`
- 相对路径，例如 `orders`

解析示例：

```text
环境 Base URL：https://test.example.com/api/
目标：orders
最终：https://test.example.com/api/orders
```

```text
环境 Base URL：https://test.example.com/api/
目标：/orders
最终：https://test.example.com/orders
```

普通场景绑定环境后，即使填写了其他域名的绝对 URL，最终执行也会使用环境的 scheme 和 host，并保留目标 URL 的 path 和 query。

mixed 场景中的绝对 HTTP(S) URL按原地址执行；相对 URL 按方案目标和环境 Base URL 解析。

执行记录会保存解析结果快照。环境配置以后发生变化，不会修改历史报告。

### 7.3 Params

Params 使用键值行编辑并合并到 URL 查询参数中。同名参数以当前编辑值为准。

### 7.4 Headers

Headers 使用键值行编辑。敏感值建议使用变量引用，不要直接写入明文：

```text
Authorization: Bearer {{secret.api_token}}
```

### 7.5 Body

- 当前页面会校验非空 Body 是否为合法 JSON；若接口接收 JSON，还应设置正确的 `Content-Type`。
- 可点击 **格式化 JSON** 检查和整理格式。
- GET 请求通常不需要 Body。

### 7.6 高级模式

高级模式允许直接编辑 Headers JSON 和 Body JSON，适合复杂请求。保存前仍会执行格式校验。

## 8. 发送一次测试请求

在请求配置区选择在线执行器，点击 **发送一次测试请求**。

此功能用于：

- 确认执行器能够访问目标地址。
- 验证 Method、URL、Headers 和 Body 是否正确。
- 在正式加压前发现网络、认证或脚本问题。

冒烟测试只发送一次请求：

- 1 VU
- 1 iteration
- 不创建正式测试报告
- 不参与基线、趋势和劣化比较

页面最长等待约 30 秒。超时后会请求取消；执行器会先尝试优雅停止，并在取消宽限期后强制终止，因此任务可能仍需短暂收尾。

## 9. 阈值设置

阈值用于判断测试结果是否满足性能目标。

### 9.1 内置模板

#### 宽松

```text
P95 < 800ms
错误率 < 0.05（5%）
```

#### 常规 SLA

```text
P95 < 500ms
P99 < 1000ms
错误率 < 0.01（1%）
```

#### 严格

```text
P95 < 300ms
P99 < 600ms
错误率 < 0.005（0.5%）
```

点击模板会替换当前阈值列表。

### 9.2 阈值字段

| 字段 | 说明 |
| --- | --- |
| 指标 | 例如请求耗时、失败率、请求数、等待时间 |
| 聚合方式 | 例如 avg、p(95)、p(99)、rate、count |
| 运算符 | `<`、`<=`、`>`、`>=` |
| 阈值 | 目标数值 |
| 自动停止 | 阈值失败后是否允许提前终止 |
| 延迟评估 | 开始执行多久后才允许自动停止，例如 `10s` |

常用指标：

| 指标 | 常用聚合 | 单位/填写方式 |
| --- | --- | --- |
| `http_req_duration` | avg、p(90)、p(95)、p(99) | 毫秒 |
| `http_req_failed` | rate | `0~1` 小数 |
| `http_reqs` | count、rate | 次数或每秒 |
| `http_req_waiting` | avg、p(95)、p(99) | 毫秒 |
| `iterations` | count、rate | 次数或每秒 |
| `iteration_duration` | avg、p(95)、p(99) | 毫秒 |

### 9.3 自动停止

启用 **停止** 后，系统生成 k6 `abortOnFail` 配置。

- `delayAbortEval` 只在自动停止开启时有效。
- 延迟评估必须是合法 k6 时长，例如 `10s`、`1m`。
- 提前终止的执行状态为“性能未达标”，并保留部分指标和趋势。

可点击 **查看生成的 k6 配置** 检查阈值表达式。

## 10. 保存与触发执行

### 10.1 保存方案

点击 **保存方案**。系统会校验：

- 项目和方案名称
- URL
- Body JSON
- VU、时长和阶段
- mixed 权重和接口配置
- 阈值字段
- 自动停止延迟格式

### 10.2 执行确认

在方案列表点击 **触发**，或在方案详情点击 **触发执行**。

确认面板展示：

- 方案和场景
- 最终目标预览
- 环境
- 最大并发
- 预计时长
- 阈值
- 在线执行器数量
- 是否已有同方案活动任务

### 10.3 本次环境覆盖

可以在执行确认中选择其他环境。该选择只影响本次执行，不修改方案默认环境。

### 10.4 生产环境确认

生产环境执行需要二次确认。首次点击 **确认执行** 后，输入完整方案名称，再点击 **确认并执行**；输入不一致时不能执行。

### 10.5 并发限制

- 最大并发不得超过 500 VU。
- 同一方案同时只允许一个活动执行。
- 定时触发遇到同方案活动执行时会跳过本次触发。

## 11. 执行状态说明

### 11.1 中间状态

| 状态 | 说明 |
| --- | --- |
| pending | 运行记录已创建 |
| queued | 等待可用执行器或槽位 |
| dispatching | 正在向执行器提交任务 |
| dispatched | 执行器已接收任务 |
| running | k6 已启动 |
| stopping | 正在停止 k6 并收集部分结果 |

### 11.2 最终状态

| 状态 | 页面含义 | 说明 |
| --- | --- | --- |
| completed | 通过 | 正常完成，所有阈值通过 |
| threshold_failed | 性能未达标 | 有有效结果，但至少一个阈值失败 |
| execution_failed | 执行异常 | 脚本、执行器、k6 或回调链路异常 |
| timed_out | 超时 | 超过动态超时并被终止 |
| canceled | 已取消 | 用户主动取消，通常保留部分结果 |

“性能未达标”和“执行异常”含义不同。前者说明测试有效但指标未通过；后者说明压测链路本身出现问题。

## 12. 实时监控

运行详情页实时展示：

- 当前状态和 SSE 连接状态
- 执行器
- 当前阶段和剩余时间
- 当前 VU
- 当前 RPS
- 当前 P95
- 错误率
- RPS 趋势
- P50/P90/P95/P99 延迟趋势
- 错误率趋势
- 活跃 VU 趋势
- HTTP 状态码分布
- 错误 Top N
- 实时阈值状态
- 脱敏事件消息

SSE 断线时页面会自动重连。断线只表示实时监控连接中断，**不会暂停、取消或判定压测失败**。最终结果以执行记录和持久化 series 为准。

平台最多保留约 3000 个趋势点；长时间测试会进行降采样，并尽量保留首尾和负载阶段边界。

## 13. 取消执行

在报告列表点击 **取消**，或在运行详情点击 **取消执行**。

取消流程：

1. 发送优雅停止信号。
2. 等待 k6 输出结果。
3. 超过宽限期后强制终止。
4. 保存已采集的部分指标。

取消后的结果不会被伪造为 0；无法采集的数据会显示为空。

## 14. 测试报告功能

报告列表支持按方案和状态筛选，并可选择 **仅看进行中**；启用后可点击 **显示全部** 恢复完整列表。

### 14.1 结论

展示：

- 通过、性能未达标或执行异常
- 场景、环境和目标
- 环境 Base URL 和最终目标地址（存在环境解析信息时）
- 执行时间和配置版本
- P95、P99、错误率、RPS、总请求数

### 14.2 阈值结果

展示每条阈值的：

- 表达式
- 实际值
- 目标值
- 差距
- 通过/失败

### 14.3 趋势与分布

展示持久化时序、状态码、错误分布和实时阈值。无数据时显示明确空态，不使用零值替代。

### 14.4 诊断信息

展示：

- 执行器和 k6 版本
- 退出码
- 失败阶段
- 任务 ID
- 执行耗时
- 错误信息
- 脱敏执行输出
- 原始 summary
- 方案执行快照

执行输出只保留脱敏后的最后约 32 KiB，不等同于完整 k6 日志。

## 15. 基线和性能回归比较

### 15.1 设置基线

只有状态为 **通过（completed）** 且指标完整的执行才能设为基线。

基线至少需要：

- 总请求数大于 0
- P95、P99 存在
- 错误率在 `0~1`
- RPS 大于 0

同一“方案 + 场景 + 环境”只有一个当前基线。使用环境 ID 时按环境 ID 区分；没有环境 ID 时按环境名称区分。重新设置会替换旧基线。

### 15.2 劣化规则

系统固定使用 10% 作为劣化判断线：

- P95 上升超过 10%：劣化
- P99 上升超过 10%：劣化
- 错误率上升超过 10%：劣化
- RPS 下降超过 10%：劣化

恰好 10% 不判定为劣化。

发生劣化时，系统向触发用户发送站内警告通知，并按执行记录去重。

### 15.3 同方案趋势

报告页可查看同一方案、场景和环境下的历史趋势：

- P95
- P99
- 错误率
- RPS

基线点和劣化点会单独标识。

## 16. 报告导出

当前页面在执行状态为 `completed` 或 `threshold_failed` 时支持：

- 导出 CSV
- 导出 JSON

### 16.1 CSV

CSV 适合表格分析，包含方案、环境、状态、时间、P95/P99、错误率、RPS、基线和劣化信息。文件使用 UTF-8 BOM，并防止公式注入。

### 16.2 JSON

JSON 适合系统集成和脱敏后的报告归档，包含：

- 运行和环境信息
- 方案快照
- 聚合指标
- 阈值
- series
- 基线比较
- 诊断摘要

导出会递归脱敏 Authorization、Cookie、Password、Token、Secret、API Key 等字段，并移除回调凭据、幂等键和调度 claim 信息。

JSON 不包含完整原始日志，也不保证保留降采样前的全部原始趋势点。

## 17. 定时规则

进入 **性能测试 → 定时规则**，点击 **新增规则**。

### 17.1 字段说明

| 字段 | 说明 |
| --- | --- |
| 规则名称 | 用于识别定时任务 |
| 方案 | 定时触发的压测方案 |
| 环境 | 可固定环境 ID；留空时跟随方案默认环境 |
| Cron | 严格五字段：分、时、日、月、星期 |
| IANA 时区 | 例如 `Asia/Shanghai`、`UTC` |
| 保存后启用规则 | 创建后是否立即开始调度 |

### 17.2 Cron 示例

| 需求 | Cron |
| --- | --- |
| 每天凌晨 1 点 | `0 1 * * *` |
| 每小时整点 | `0 * * * *` |
| 每周一上午 9 点 | `0 9 * * 1` |
| 工作日凌晨 2 点 | `0 2 * * 1-5` |
| 每月 1 日凌晨 3 点 | `0 3 1 * *` |

Cron 不支持秒字段，也不支持 `@daily`、`@every` 等简写。

### 17.3 规则操作

- 搜索、重置、刷新
- 新增规则
- 编辑
- 启用/停用
- 删除
- 点击上次结果跳转到对应报告

### 17.4 调度结果

| 结果 | 说明 | 建议 |
| --- | --- | --- |
| 已触发 | 已创建或复用本次执行 | 查看报告 |
| 已有活动任务，已跳过 | 同一方案正在执行 | 等待当前任务结束 |
| 已阻止 | 方案、环境或 Cron 存在永久性问题 | 修复配置后重新启用 |
| 执行错误 | 本轮调度发生临时系统错误 | 查看错误信息并重试 |

停用或删除定时规则不会取消已经创建的运行。

## 19. 常见问题

### 19.1 提示“未安装 k6”

在执行器机器安装 k6，并确认执行器进程的 `PATH` 可以找到 k6。重启执行器后再检查在线状态。

### 19.2 一直处于 queued

可能原因：

- 没有在线且支持性能测试的执行器。
- 执行器性能测试槽位已占用。
- 同一方案存在活动任务。

### 19.3 mixed 权重校验失败

确保所有接口权重均大于 0，且合计等于 1。例如：

```text
0.6 + 0.3 + 0.1 = 1
```

### 19.4 错误率阈值如何填写

错误率使用小数：

| 目标 | 填写值 |
| --- | --- |
| 低于 5% | `0.05` |
| 低于 1% | `0.01` |
| 低于 0.5% | `0.005` |

### 19.5 实时监控断线是否会停止压测

不会。SSE 只负责展示实时数据，压测任务继续在执行器运行。页面会自动重连，最终以报告数据为准。

### 19.6 threshold_failed 是否表示系统故障

不是。它表示测试执行有效，但至少一个性能阈值未通过。执行链路故障对应 `execution_failed`。

### 19.7 为什么不能设置基线

只有指标完整的 `completed` 记录可以设为基线。性能未达标、执行失败、超时和取消记录不能作为基线。

### 19.8 定时规则为何显示“已跳过”

同一方案已有活动执行时，系统不会重复施压，而是跳过本次定时触发。

## 20. 安全建议

- 生产环境压测前完成审批和容量评估。
- 先执行冒烟和低并发 baseline，再逐步加压。
- 不在方案中保存明文密码、Token、Cookie 或 API Key。
- 使用 `{{secret.NAME}}` 引用敏感变量。
- 确认测试账号、测试数据和清理策略。
- 避免在业务高峰执行 peak、stress 或高并发 mixed。
- 同时观察服务端、数据库和基础设施监控。
- 测试结束后检查错误日志、告警和残留数据。
